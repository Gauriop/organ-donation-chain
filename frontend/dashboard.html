Living Donors

donor_living — horizontal fragment of donor table

⚡ Fragmentation Query Running 🔀 Horizontal
📌 Why this fragment? Living and deceased donors have completely different workflows — living donors need health monitoring, deceased donors need rapid organ harvesting. Splitting by donor_type avoids scanning deceased records when looking for living donors and vice versa.
-- Fragment Table: donor_living -- Created by: CREATE TABLE donor_living AS SELECT * FROM donor WHERE donor_type = 'Living' -- This query runs on the FRAGMENT, not the full donor table SELECT d.*, h.name AS hospital_name FROM donor_living d ← horizontal fragment (only Living rows) JOIN hospital h ON d.hospital_id = h.hospital_id ORDER BY d.donor_id DESC; -- Without fragmentation (SLOW): scans ALL 50+ donors -- SELECT * FROM donor WHERE donor_type = 'Living'; ← full table scan -- With fragmentation (FAST): scans only living donor rows directly

🔗 How Donation Chains Work
Step 1
Donor A can't directly donate to Recipient A (blood mismatch). But Donor A CAN donate to Recipient B.
Step 2
Recipient B's family member (Donor B) agrees to donate to Recipient A — completing the chain.
Result
Both A and B get organs they couldn't get directly. More lives saved through chained exchanges.

Transplant Medical Details

transplant_medical + transplant_details — vertical fragments of transplant_record

⚡ Fragmentation Query Running ↕ Vertical
📌 Why this fragment? Transplant_Record has 9 columns — admin staff need status/dates, doctors need surgeon/outcome. Vertical split means smaller row sizes, better cache utilization, and access control (doctors can't see admin fields and vice versa).
-- Vertical Fragment 1: transplant_medical (clinical columns) -- CREATE TABLE transplant_medical AS SELECT transplant_id, staff_id, outcome FROM transplant_record SELECT tm.*, ms.name AS surgeon_name FROM transplant_medical tm ← only staff_id + outcome columns JOIN medical_staff ms ON tm.staff_id = ms.staff_id; -- Vertical Fragment 2: transplant_details (admin columns) -- CREATE TABLE transplant_details AS SELECT transplant_id, organ_id, donor_id, recipient_id, hospital_id, surgery_date, status FROM transplant_record SELECT td.*, h.name AS hospital_name FROM transplant_details td ← admin columns only JOIN hospital h ON td.hospital_id = h.hospital_id; -- Reconstruction JOIN (lossless — both share transplant_id PK): -- SELECT * FROM transplant_details td JOIN transplant_medical tm USING (transplant_id)

Available Organs

organ_available — horizontal fragment of organ table

⚡ Fragmentation Query Running 🔀 Horizontal
📌 Why this fragment? 90% of organ queries are for Available status — doctors matching organs to recipients. By isolating Available organs, we skip scanning Allocated/Transplanted/Expired rows entirely. Critical in time-sensitive transplants.
-- Fragment: organ_available (status = 'Available' only) -- CREATE TABLE organ_available AS SELECT * FROM organ WHERE status = 'Available' SELECT o.*, d.name AS donor_name, d.blood_type, h.name AS hospital_name, ROUND(EXTRACT(EPOCH FROM (o.expiry_time - NOW()))/3600, 1) AS hours_remaining FROM organ_available o ← fragment table, not full organ table JOIN donor d ON o.donor_id = d.donor_id JOIN hospital h ON d.hospital_id = h.hospital_id ORDER BY o.expiry_time ASC NULLS LAST; ← soonest expiry first

Critical Waitlist

waitlist_critical — horizontal fragment by urgency level

⚡ Fragmentation Query Running 🔀 Horizontal
📌 Why this fragment? Critical patients need immediate attention — doctors check this 10x more than Low/Medium. Dedicated fragment means zero time wasted scanning non-critical entries. This is the most performance-critical query in the system.
-- Fragment: waitlist_critical (joined with recipient WHERE urgency = 'Critical') -- CREATE TABLE waitlist_critical AS -- SELECT w.* FROM waitlist w JOIN recipient r ON w.recipient_id = r.recipient_id -- WHERE r.urgency_level = 'Critical' SELECT w.*, r.name AS recipient_name, r.blood_type, r.urgency_level, h.name AS hospital_name, (CURRENT_DATE - w.registration_date) AS days_waiting FROM waitlist_critical w ← Critical-only fragment JOIN recipient r ON w.recipient_id = r.recipient_id JOIN hospital h ON r.hospital_id = h.hospital_id ORDER BY w.priority_score DESC; ← highest priority first

Compatibility Summary

compat_summary — vertical fragment of compatibility_test

⚡ Fragmentation Query Running ↕ Vertical
📌 Why this fragment? Dashboard only needs pass/fail result — not blood_match boolean, tissue_match boolean, or compatibility_score decimal. Vertical fragmentation splits columns: compat_summary (basic result) vs compat_detail (full scores). Smaller rows = faster scans.
-- Fragment: compat_summary (VERTICAL split — selected columns only) -- CREATE TABLE compat_summary AS -- SELECT test_id, donor_id, recipient_id, test_date, test_result -- FROM compatibility_test; ← no blood_match, tissue_match, compatibility_score SELECT cs.*, d.name AS donor_name, r.name AS recipient_name FROM compat_summary cs ← vertical fragment (5 cols, not 8) JOIN donor d ON cs.donor_id = d.donor_id JOIN recipient r ON cs.recipient_id = r.recipient_id ORDER BY cs.test_date DESC; -- For full scores, doctors use compat_detail (different fragment): -- SELECT * FROM compat_detail WHERE test_id = ? ← joins by test_id
